⚖️ Legal & Ethical Guidelines

Understanding legal requirements and ethical responsibilities is critical before conducting any security assessment.

🔒 Authorization & Scope

✅ Written Authorization Required
Always obtain written, signed authorization from system owner or authorized representative before beginning any assessment. Include: Scope (systems/networks), timeframe, testing methods allowed, emergency contacts.

📋 Rules of Engagement (ROE)

  • Define Scope: Clearly document what systems, networks, and data are in scope
  • Exclude Systems: Identify systems that are out of scope (production, third-party, partner systems)
  • Testing Hours: Specify when testing can occur to avoid business disruption
  • Methods Allowed: Agree on which testing techniques are permitted (DoS testing, password spraying, etc.)
  • Data Handling: Define how sensitive data discovered will be handled and protected
  • Communication Protocol: Establish how critical findings will be reported during assessment
  • Emergency Contact: Provide contact info for stopping assessment if issues arise

⚠️ Legal Compliance

🇺🇸 United States

  • Computer Fraud & Abuse Act (CFAA) - Authorization required
  • DMCA - Anti-circumvention provisions apply
  • State laws - Additional restrictions vary by state
  • Wiretap laws - Don't intercept communications without authorization

🇪🇺 Europe & GDPR

  • GDPR - Protect personal data discovered during testing
  • PECR - Electronic communications regulations
  • National cybercrime laws - Vary by country
  • Processor Agreements - May need data processing agreements

🚫 Activities That Require Explicit Permission

  • ❌ Denial of Service (DoS) or DDoS testing
  • ❌ Password spraying or brute force attacks
  • ❌ Social engineering or phishing campaigns
  • ❌ Accessing production systems without approval
  • ❌ Modifying or deleting data
  • ❌ Creating backdoors or persistence mechanisms
  • ❌ Testing authentication systems
  • ❌ Accessing protected health information (PHI)
  • ❌ Credit card data testing (PCI-DSS)

💡 Ethical Principles

1. Get Written Permission

Never test without explicit, written authorization from the system owner. Verbal permission is not sufficient.

2. Stay In Scope

Only test systems and networks that are explicitly authorized. Do not explore adjacent systems.

3. Don't Cause Damage

Conduct testing carefully to avoid disrupting services, deleting data, or harming systems.

4. Report Responsibly

Report findings to the authorized contact immediately. Don't disclose vulnerabilities publicly.

3. Protect Privacy

Keep all findings confidential. Secure any data extracted during testing.

⚙️ Phase 2: Environment Setup (30-45 minutes)

Step 1: Enable Hyper-V on Windows

1.1a

Open PowerShell as Administrator (Method 1: Start Menu)

  1. Click Windows Start Button (bottom left)
  2. Type: PowerShell
  3. Right-click on Windows PowerShell result
  4. Select Run as administrator
  5. Click Yes when UAC prompt appears
  6. Wait for blue PowerShell window to open
  7. Verify prompt shows: PS C:\Windows\system32>
1.1b

Open PowerShell as Administrator (Method 2: Keyboard)

  1. Press: Windows Key + X
  2. Select: Windows PowerShell (Admin)
  3. Click Yes on UAC prompt
  4. Ready to run commands
1.2

Check if Hyper-V is Already Enabled

In PowerShell, type and press Enter:

Get-WindowsOptionalFeature -FeatureName Hyper-V -Online

Expected Output - Check the "State" line:

FeatureName : Hyper-V DisplayName : Hyper-V Description : Hyper-V RestartRequired : False State : Enabled CustomProperties :
✓ If you see "State : Enabled" → Jump directly to Step 3: Create Hyper-V Virtual Network
If you see "State : Disabled" → Continue to Step 1.3 below
1.3

Enable Hyper-V (If Currently Disabled)

⚠️ WARNING: Your computer WILL RESTART

Save ALL open files and close applications before continuing. You have ~30 seconds to cancel after running the command.

In PowerShell (still as Administrator), type and press Enter:

Enable-WindowsOptionalFeature -FeatureName Hyper-V -Online -All

What you'll see:

Path : Online : True RestartNeeded : True

When asked "Do you want to restart the computer now?", press:

Y # Then press Enter

Your computer will:

  1. Show "Shutting down..." message
  2. Restart automatically (2-5 minutes)
  3. Show Windows logo during boot
  4. Return to login screen

After restart:

  1. Login to Windows
  2. Wait 2-3 minutes for Hyper-V services to fully load
  3. Open PowerShell again as Administrator
  4. Run verification command again to confirm Hyper-V is enabled
✓ Hyper-V is now enabled! Proceed to Step 3.

Step 2: Create Hyper-V Virtual Network (Bridge Mode)

2.1a

Open Hyper-V Manager (Method 1: Run Dialog)

  1. Press Windows Key + R on your keyboard
  2. A "Run" dialog box will appear in the center of screen
  3. Type exactly: virtmgmt.msc
  4. Press Enter
  5. Wait 3-5 seconds for Hyper-V Manager to open
  6. You'll see a window with "Hyper-V Manager" in the title bar
2.1b

Open Hyper-V Manager (Method 2: Start Menu)

  1. Click Windows Start button
  2. Search: Hyper-V
  3. Click Hyper-V Manager in results
  4. Wait for application to load
2.2

Verify You're in Hyper-V Manager

You should see a window with:

  • Title bar says: "Hyper-V Manager"
  • Left panel has: "Hyper-V Manager [your computer name]"
  • Right panel has buttons: New, Connect, Import, etc.
[Hyper-V Manager window with left panel showing server name]
2.3

Find Virtual Switch Manager Button

  1. Look at the RIGHT PANEL of Hyper-V Manager
  2. You should see buttons like: New, Connect, Settings
  3. Look for "Virtual Switch Manager" button (may be under "Actions" menu)
  4. If you don't see it directly:
    • Look at the top menu bar
    • Click Actions menu
    • Find Virtual Switch Manager option
    • Click it
2.4

Create New Virtual Switch - Step by Step

In Virtual Switch Manager window:

  1. Left panel: Select "New virtual switch"
  2. Middle panel - Virtual switch type:
    • You'll see 3 radio button options
    • Select the radio button next to "External"
    • (This allows VM to access your network)
  3. Then: Click blue button "Create Virtual Switch"
2.5

Configure Virtual Switch Settings

A new dialog will open with configuration options:

  1. Name field:
    • Clear any existing text
    • Type: Kali-Bridge
  2. Connection type:
    • Verify "External" is selected
  3. External network dropdown:
    • Click the dropdown menu
    • Select your network adapter (usually "Ethernet" or "WiFi")
    • If you see multiple options, pick the one labeled with your internet connection
  4. Options (leave as default):
    • ☑ "Allow management operating system to share this network adapter"
    • (This should be checked)
[Virtual Switch configuration dialog showing Kali-Bridge name and External selection]
2.6

Finalize Virtual Switch Creation

  1. After filling in all settings above, click button "OK"
  2. Hyper-V will create the switch (takes 5-10 seconds)
  3. You might see a warning about network interruption - this is normal
  4. Your internet might disconnect briefly and reconnect
  5. Wait for Virtual Switch Manager to close
✓ Virtual switch "Kali-Bridge" created successfully!

Your Kali VM will now have network access just like your Windows machine.

Step 3: Import Kali Linux VM

3.1

Download Kali Hyper-V Image (If Not Already Done)

  1. Go to: https://www.kali.org/get-kali/
  2. Find "Hyper-V" section
  3. Click download button (file size ~3-4 GB)
  4. Save to your Downloads folder or preferred location
  5. Wait for download to complete (may take 10-30 minutes depending on internet)
3.2

Extract Kali ZIP File

  1. Open File Explorer (Windows folder icon)
  2. Navigate to where Kali ZIP file is (usually Downloads)
  3. Right-click on Kali-Linux-*.zip file
  4. Select Extract All...
  5. A dialog will open asking where to extract
  6. Choose location (e.g., C:\VMs\Kali)
  7. Click Extract
  8. Wait for extraction (2-5 minutes)
3.3

Verify Extracted Files

  1. In File Explorer, open the extracted folder
  2. You should see these files:
    • Kali-Linux.vhdx (large file, 3-4 GB)
    • Kali-Linux.vmcx or similar config file
    • Possibly a Snapshots folder
  3. Remember this folder path! You'll need it in the next step
  4. Example path: C:\VMs\Kali or C:\Users\YourName\Downloads\Kali-Linux
✓ Kali files extracted successfully!
3.4

Import VM into Hyper-V - Part 1

  1. Go back to Hyper-V Manager window
  2. In the LEFT PANEL, you should see your computer name (e.g., "MY-COMPUTER")
  3. Right-click on your computer name
  4. A menu will appear
  5. Click Import Virtual Machine...
3.5

Import VM into Hyper-V - Part 2: Select Folder

An "Import Virtual Machine" dialog will open:

  1. You'll see text: "Locate Folder"
  2. Click the Browse... button
  3. Navigate to the Kali extracted folder (from Step 3.3)
  4. Select the folder containing the .vhdx file
  5. Click Select Folder
  6. You'll see the path appear in the dialog
  7. Click Next
3.6

Import VM into Hyper-V - Part 3: Choose Import Type

You'll see two options:

  • Restore the virtual machine (copies files)
  • Register the virtual machine in-place (uses files as-is)

SELECT: "Register the virtual machine in-place"

(This is faster and you keep the files in the same location)

Click Next

3.7

Import VM into Hyper-V - Part 4: Review Summary

  1. The wizard shows a summary of VM details
  2. You'll see: Name, Memory, Processor, Network Adapter info
  3. Verify it looks correct
  4. Click Finish

Hyper-V will now import the VM:

  • A progress bar may appear
  • Takes 30 seconds to 2 minutes
  • When done, you'll return to main Hyper-V Manager window
✓ Kali VM imported! You should now see it in the Hyper-V Manager list.
3.8

Verify VM Was Imported

  1. In Hyper-V Manager, look at the MIDDLE PANEL
  2. You should see a list of VMs
  3. Find "Kali-Linux" or similar name
  4. Status should show "Off" (not running yet)
[Hyper-V Manager showing Kali-Linux VM in the list with status "Off"]
3.9

Configure Network for Kali VM

  1. In Hyper-V Manager middle panel, find Kali VM
  2. Right-click on Kali-Linux
  3. Select Settings...
  4. A Settings window will open on the left with options
  5. Find and click on Network Adapter
3.10

Set Network Adapter to Kali-Bridge

  1. In the right panel under "Network Adapter" settings
  2. Find dropdown labeled "Virtual switch:"
  3. Click the dropdown
  4. Select Kali-Bridge (the one we created in Step 2)
  5. You should see it selected
  6. Click OK button at bottom of window
✓ Kali VM configured to use Kali-Bridge network!
3.11

Start Kali VM - Part 1

  1. Back in Hyper-V Manager main window
  2. Find Kali VM in the middle panel
  3. Right-click on Kali-Linux
  4. Select Start
  5. VM status will change from "Off" to "Running"
3.12

Open Kali VM Console

  1. Still in Hyper-V Manager
  2. Double-click on Kali-Linux VM
  3. A window will open showing Kali desktop
  4. Wait 2-3 minutes for Kali to fully boot
  5. You'll see Kali login screen or desktop
[Kali VM console window showing login prompt or desktop]
3.13

Login to Kali VM

  1. If you see a login prompt, click in the username field
  2. Type: kali
  3. Press Tab or click password field
  4. Type: kali
  5. Press Enter
  6. Wait 10-20 seconds for desktop to load
✓ You're now logged into Kali Linux!

You should see the Kali desktop with taskbar at bottom.

Step 4: Install Framework Prerequisites on Kali

4.1a

Open Terminal on Kali VM

  1. In Kali console window, look for terminal icon in taskbar
  2. Or right-click on desktop and select "Open Terminal Here"
  3. A black terminal window will open
  4. You should see prompt like: kali@kali:~$
4.1b

Update Kali System - Part 1

Type this command and press Enter:

sudo apt-get update

What you'll see:

  • Lines of text showing package sources being checked
  • May ask for password (type: kali)
  • Ends with: "All packages are up to date" or similar
  • Takes 1-2 minutes
4.1c

Update Kali System - Part 2

Next, type and press Enter:

sudo apt-get upgrade -y

What happens:

  • Shows list of packages to upgrade
  • The -y flag automatically says "yes"
  • Packages download and install
  • This takes 5-15 minutes depending on updates needed
  • When done, you'll see the prompt again: kali@kali:~$
ℹ️ Be patient! This step is crucial for security. Don't close terminal.
4.2a

Install Node.js - Part 1

Type and press Enter:

sudo apt-get install -y nodejs npm

Expected output:

  • Shows packages being downloaded
  • Shows packages being unpacked and set up
  • Takes 2-3 minutes
  • Ends with prompt: kali@kali:~$
4.2b

Verify Node.js Installation

Type and press Enter:

node --version

You should see:

v18.17.0 # or similar version 16+ or 18+

Now check npm:

npm --version

You should see:

9.6.7 # or similar version 8+ or 9+
✓ Node.js and npm installed! Both commands should return version numbers.
4.3a

Install Git

Type and press Enter:

sudo apt-get install -y git

Expected output:

  • Shows git being installed
  • Takes 1-2 minutes
  • Ends with prompt
4.3b

Verify Git Installation

Type and press Enter:

git --version

You should see:

git version 2.39.0 # or similar 2.x version
4.4a

Install SSH Server

Type and press Enter:

sudo apt-get install -y openssh-server openssh-client

What you'll see:

  • Shows SSH being installed
  • Takes 1-2 minutes
4.4b

Start SSH Service

Type and press Enter:

sudo systemctl start ssh

No output = success (just returns to prompt)

4.4c

Enable SSH to Start on Boot

Type and press Enter:

sudo systemctl enable ssh

You'll see:

Synchronizing state of ssh.service with SysV service script with /lib/systemd/systemd-sysv-install. Executing: /lib/systemd/systemd-sysv-install enable ssh
4.4d

Verify SSH is Running

Type and press Enter:

False positives reduce confidence in reports and waste remediation resources. This section covers verification techniques.

🔍 Common False Positive Sources

🤖 Scanner Errors

  • Regex pattern over-matching
  • Timing-based assumptions
  • Cookie/session handling
  • JavaScript rendering issues
  • Form state tracking

🔐 Security Controls

  • Web Application Firewall (WAF) blocks
  • Rate limiting triggers
  • CORS policy restrictions
  • CSP header prevents exploitation
  • Input sanitization works

🛠️ Configuration Issues

  • Scanner misconfiguration
  • Wrong credentials used
  • Network routing issues
  • Proxy interference
  • Encoding mismatches

🎭 Detection Evasion

  • Intentional honeypot fields
  • Fake error messages
  • Decoy pages/endpoints
  • Hardened test environments

✅ Verification Techniques

Finding Type Verification Step Success Criteria
SQL Injection Run payload, verify database error or data extraction Can dump data or execute commands

📊 False Positive Reduction Workflow

1. Initial Finding

Tool reports potential vulnerability. Note tool confidence level and description.

2. Manual Reproduction

Manually attempt to reproduce using exact steps. If fails, likely false positive.

3. Verify Exploitation

If reproduced, confirm actual exploitation impact (not just presence).

4. Check Mitigations

Verify if existing controls (WAF, filters, rate limits) actually prevent exploitation.

5. Document Result

Record: Real vulnerability, False positive, or Mitigated finding. Document reason.

🔧 Remediation & Fix Guide

Step-by-step guidance for fixing each vulnerability type. Organize fixes by CVSS severity.

🔴 CRITICAL Vulnerabilities (CVSS 9.0+)

💥 SQL Injection (Critical)

Root Cause: Unparameterized SQL queries with user input

Fix Steps:

  1. Replace all concatenated SQL queries with parameterized queries
  2. Use ORM frameworks (SQLAlchemy, Hibernate) if possible
  3. Implement input validation (whitelist allowed characters)
  4. Use database permissions (user account with minimal privileges)
  5. Enable SQL query logging and monitoring
  6. Test fix: Verify injection payload rejected

Code Example:

# ❌ VULNERABLE
query = "SELECT * FROM users WHERE id=" + user_input

# ✅ FIXED
cursor.execute("SELECT * FROM users WHERE id=?", (user_input,))

🔓 Authentication Bypass (Critical)

Root Cause: Weak or missing authentication checks

Fix Steps:

  1. Add authentication check to all protected endpoints
  2. Verify JWT/session token validity on every request
  3. Implement proper session management (secure cookies)
  4. Add multi-factor authentication (MFA)
  5. Implement rate limiting on login endpoint
  6. Log all authentication failures

Verification: Access protected resource without credentials (should fail)

🟠 HIGH Vulnerabilities (CVSS 7.0-8.9)

  • Cross-Site Scripting (XSS): Implement output encoding, CSP headers, input validation
  • Remote Code Execution (RCE): Disable dangerous functions, use sandboxing, input validation
  • Insecure Deserialization: Don't deserialize untrusted data, use JSON instead, implement signing
  • Broken Authorization: Verify user permission for EVERY action, implement role-based access control

🟡 MEDIUM Vulnerabilities (CVSS 4.0-6.9)

  • Information Disclosure: Remove debug info, disable verbose errors, implement proper logging
  • Weak Cryptography: Use AES-256, modern TLS versions, never use MD5/SHA1
  • Insecure Direct Object References (IDOR): Validate user authorization before accessing resource
  • Security Misconfiguration: Apply security hardening, implement defaults securely

🔄 Retesting & Verification Procedures

How to confirm that fixes actually resolve vulnerabilities. Includes regression testing.

✅ Retesting Workflow

Step 1: Schedule Retest

Coordinate with dev team. Verify fixes deployed to test environment. Allow time for thorough testing.

Step 2: Prepare Test Environment

Restore baseline snapshot. Apply fixes only. Verify no unrelated changes.

Step 3: Re-Execute Original Tests

Use exact same test cases that found original vulnerability. Verify payload/attack fails now.

Step 4: Verify Variations

Test similar attack vectors. Ensure fix doesn't just block specific payload.

Step 5: Regression Testing

Run full assessment again to ensure fixes didn't introduce new vulnerabilities.

Step 6: Document Results

Record: Fixed, Still Vulnerable, Partially Mitigated. Include evidence (screenshots, logs).

🔍 Retesting Checklist

  • ✔️ Original Payload Tested: Same attack that found vulnerability attempted again

  • ✔️ Legitimate Traffic Works: Normal application functionality not broken
  • ✔️ Regression Testing Done: Full security scan to find new issues
  • ✔️ Hotfixes Included: Any emergency patches applied correctly
  • ✔️ Configuration Verified: Security settings applied across all environments
  • ✔️ Monitoring Enabled: Logging/alerting for this vulnerability type active

Error: "Could not resolve hostname"

Solution:

  • Verify IP: hostname -I on Kali
  • Ping Kali from Windows: ping 192.168.1.100
  • Check Hyper-V bridge network settings

SSH Permission Denied

Error: "Permission denied, please try again"

Solution:

  • Default creds: kali/kali (case-sensitive)
  • Check Caps Lock
  • Reset password on Kali if needed

Assessment Timeout

Error: "Assessment timeout"

Solution:

  • Select faster intensity level (Rapid)
  • Increase timeout: ASSESSMENT_TIMEOUT=7200000 npm run assess
  • Check network connectivity

Report Not Generated

Error: "report-*.json not found"

Solution:

  • Check if assessment fully completed
  • Review logs: tail logs/error.log
  • Verify disk space: df -h

Understanding Severity Levels

Level CVSS Range Action Required Timeline
CRITICAL 9.0 - 10.0 Fix immediately, take system offline if needed 24 hours
HIGH 7.0 - 8.9 Schedule emergency fix 3-7 days
MEDIUM 4.0 - 6.9 Plan fix in next sprint/release 2-4 weeks
LOW 0.1 - 3.9 Document and track, fix in backlog 1-3 months
INFO 0.0 Informational only, no action needed N/A

How to Interpret CVSS Score

  • 9.0-10.0 (CRITICAL): Remote network access, no authentication needed, major impact
  • 7.0-8.9 (HIGH): Network accessible, may need some authentication, significant impact
  • 4.0-6.9 (MEDIUM): Local access or limited network impact, or low impact remote issue
  • 0.1-3.9 (LOW): Requires special conditions, limited impact, difficult to exploit

🛑 How to Stop or Abort Assessment

Graceful Shutdown (Recommended)

# In the assessment terminal, press Ctrl+C ^C # Assessment will: # 1. Stop current test # 2. Generate partial report # 3. Save findings so far # 4. Display summary

Force Kill (If Stuck)

# Find assessment process ps aux | grep assess # Kill specific process kill -9 [PID] # Or kill all Node processes (careful!) pkill -9 node

Disconnect SSH While Assessment Runs

# Press Ctrl+D to logout (assessment continues) ^D # Or disconnect immediately exit # Assessment continues in background # Reconnect later to check status # ssh kali@192.168.1.100 # tail -f logs/assessment.log

📖 Glossary of Security Terms

A

  • CVSS (Common Vulnerability Scoring System): Standardized method for rating vulnerability severity (0-10)
  • CWE (Common Weakness Enumeration): Categorization of software weaknesses/bugs
  • CVE (Common Vulnerabilities and Exposures): Public database of known vulnerabilities

B

  • Burp Suite: Web application security testing tool
  • BOLA (Broken Object Level Authorization): User can access objects they shouldn't

C

  • CSRF (Cross-Site Request Forgery): Attacker tricks user into unintended actions
  • Credential Testing: Attempting to access systems with provided credentials

E

  • Exploitation: Actively testing if vulnerability can be exploited
  • Enumeration: Discovering services, users, and resources on target

I

  • IDOR (Insecure Direct Object References): User can access others' resources
  • Injection: Inserting malicious code into inputs (SQL, OS, LDAP)

O

  • OWASP: Open Web Application Security Project - industry standards
  • OWASP Top 10: 10 most critical web security risks

P

  • Penetration Testing: Authorized security testing to find vulnerabilities
  • Payload: Data/code used to test for vulnerabilities

R

  • RCE (Remote Code Execution): Attacker can run code on target system
  • Reconnaissance: Gathering information about target system
  • Remediation: Fixing/patching vulnerabilities

S

  • SQLi (SQL Injection): Inserting SQL code into input fields
  • SSRF (Server-Side Request Forgery): Server makes unauthorized requests

X

  • XSS (Cross-Site Scripting): Injecting malicious scripts into web pages

❓ Frequently Asked Questions (FAQ)

Getting Started

Q: Can I test systems I don't own?
A: Only with explicit written authorization. Unauthorized testing is illegal in most jurisdictions. Always get written permission before testing.
Q: How much RAM do I need?
A: Minimum 16GB for host machine, 4GB for Kali VM. More is better for faster scanning.
Q: Can I use this on Mac/Linux instead of Windows?
A: Yes! The framework runs on any system with Node.js. Skip the Hyper-V setup and use Docker/VirtualBox instead.

Assessment Execution

Q: Why is assessment taking so long?
A: Large applications can take 2-6 hours. Thorough testing takes time. Disable unnecessary tools if needed, or switch to "Rapid" intensity.
Q: Can I test multiple targets simultaneously?
A: Not recommended. Run assessments sequentially to avoid resource contention and unclear findings.
Q: Assessment crashed, what about partial findings?
A: Check for report-*.json file. Partial reports are usually saved. Review what you have and run again if needed.

Results & Remediation

Q: Are all findings real vulnerabilities?
A: Most are, but some may be false positives. Verify critical findings before taking action.
Q: How do I know if a finding is actually exploitable?
A: The report includes proof-of-concept payloads. Try them yourself to confirm. Some vulnerabilities require specific conditions.
Q: What's the difference between vulnerability severity levels?
A: CRITICAL=fix in 24h, HIGH=1 week, MEDIUM=1 month, LOW=backlog. See Report Format Guide for details.

Technical Issues

Q: I can't connect to Kali VM via SSH
A: Check: 1) Kali VM is running, 2) Hyper-V bridge network configured, 3) Correct IP address, 4) SSH service enabled. See Troubleshooting section.
Q: Assessment can't reach target system
A: Verify: 1) Target is online and accessible, 2) Firewall allows connection, 3) Correct URL/IP entered, 4) Network is stable.
Q: Credentials not working in assessment
A: Ensure credentials are correct. Framework tries to use them as-is. If they have special characters, they may need escaping.

🔄 Multi-Agent Workflow: Step-by-Step

Step 1: Assessment Initialization

Step 2: Parallel Reconnaissance (Phase 1)

All reconnaissance agents run in parallel:

  • DNS Agent: Finds subdomains (example.com, api.example.com, admin.example.com)
  • IP Agent: Scans port ranges (finds 80, 443, 8080, 3000)
  • Service Agent: Detects services (Apache 2.4, Node.js, PostgreSQL)
  • Tech Agent: Identifies stack (React, Express, PostgreSQL)

Step 3: Data Consolidation & Dependency Detection

Orchestrator Agent collects results from all reconnaissance agents and detects dependencies for next phases.

  • Merges findings (10 subdomains, 25 open ports identified)
  • Removes duplicates (finds api.example.com from both DNS and IP scans)
  • Prioritizes targets based on findings
  • Determines which agents can run in parallel next
Step 4: Parallel Scanning (Phase 2)

Specialized agents attack different vectors simultaneously:

  • Web Scanner Agent: Tests example.com for OWASP Top 10
  • API Scanner Agent: Tests api.example.com for API vulnerabilities
  • Code Analyzer Agent: Scans for dependency vulnerabilities
  • Network Agent: Tests wireless networks & VPN configs

⏱️ Execution time: ~20-60 minutes (4 agents in parallel)

Step 5: Vulnerability Verification

Each agent independently verifies its own findings:

  • Web Scanner: Re-tests SQL injection finding twice to confirm
  • Code Analyzer: Checks if vulnerable dependency is actually used
  • Network Agent: Verifies unencrypted data transmission
  • Only confirmed findings proceed to exploitation phase
Step 6: Targeted Exploitation (Phase 3)

Exploitation Agent uses verified findings to demonstrate impact:

  • Crafts SQL injection payload based on Web Scanner findings
  • Generates exploit for known vulnerability in dependency
  • Attempts to access protected data using identified weakness
  • Documents proof-of-concept for each vulnerability

⏱️ Execution time: ~30-120 minutes (depends on vulnerability complexity)

Step 7: Post-Exploitation & Data Collection

Exploitation Agent continues with post-exploitation:

  • Extracts database contents (user credentials, PII)
  • Enumerates system information
  • Checks for lateral movement possibilities
  • Documents access level & available data
Step 8: Parallel Deep Analysis (Phase 4)

Specialized agents perform deep dives on specific areas:

  • Auth Agent: Tests 2FA bypass, session fixation, brute force
  • Crypto Agent: Analyzes encryption algorithms & key management
  • Config Agent: Audits server headers, CORS, CSP policies
  • API Agent: Tests rate limiting, authentication, authorization
Step 9: Result Aggregation & Analysis (Phase 5)

All agents submit findings to Reporting Agent:

  • Web Scanner: 12 findings (3 Critical, 4 High, 5 Medium)
  • Code Analyzer: 8 findings (0 Critical, 2 High, 6 Medium)
  • Exploitation: 4 findings (2 Critical, 2 High)
  • Network Agent: 6 findings (1 Critical, 3 High, 2 Medium)
Step 10: Deduplication & Risk Scoring

Reporting Agent deduplicates findings:

  • Finds SQL Injection reported by both Web Scanner & Exploitation Agent → Keep one entry
  • Merges findings from different agents about same vulnerability
  • Assigns risk scores based on CVSS 3.1 methodology
  • Calculates overall risk level
Step 11: Report Generation (Phase 6)

Reporting Agent generates comprehensive reports:

  • Executive Summary: 1-page overview for C-suite (2 Critical, 9 High, 13 Medium vulnerabilities, Overall Risk: HIGH)
  • Technical Report: Detailed findings with proof-of-concept code
  • Remediation Guide: Step-by-step fix instructions for each finding
  • Compliance Mapping: Links to OWASP Top 10, NIST, PCI-DSS requirements

⚡ Parallel Execution Patterns

The framework uses several patterns to maximize efficiency:

🔀 Fan-Out Pattern

One agent creates tasks for multiple specialized agents:

  • Orchestrator discovers 10 subdomains
  • Spawns 10 Scanner agents in parallel (one per subdomain)
  • Each scans independently
  • Results consolidated when all complete

Benefit: 10x faster than sequential scanning

🔗 Pipeline Pattern

Output from one agent becomes input to next:

  • Reconnaissance Agent finds vulnerabilities
  • → Web Scanner Agent tests them
  • → Verification Agent confirms them
  • → Exploitation Agent exploits them

Benefit: Progressively more certain findings

🎯 Map-Reduce Pattern

Many agents process data, results reduced to single output:

  • Map: 6 specialized agents scan simultaneously
  • Reduce: Reporting Agent consolidates findings
  • Deduplicates common vulnerabilities
  • Creates single comprehensive report

Benefit: No duplicate reporting, unified view

🔄 Feedback Loop Pattern

Results trigger additional specialized investigations:

  • Web Scanner finds SQL Injection
  • → Triggers Exploitation Agent
  • → Exploitation finds database access
  • → Triggers Data Extraction Agent

Benefit: Adaptive testing based on findings
