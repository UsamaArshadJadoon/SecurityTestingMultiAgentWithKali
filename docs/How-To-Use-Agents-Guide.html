⏱ How long does this actually take?

Setup is minutes; the 106-agent run itself is the overwhelming majority of the time. Ranges below are per-step — actual timing varies by target size and network conditions.

Step 10 — Full 106-agent run (~15h)

Why this is much longer than "a couple hours"106 agents run sequentially because later ones depend on earlier findings (Step 10's execution_context), and many individual agents genuinely take real wall-clock time against a live target — password/hash cracking (hashcat, john), WiFi handshake capture, full port/vuln scans, firmware extraction, and thorough manual-style exploitation attempts don't finish in seconds. Plan a full engagement as an overnight or unattended background run, with Step 13 used to check in periodically rather than watching it continuously.
1

Check your machine has the basics

What this does: confirms Node, Python, and Git are installed before you touch anything else — every later step depends on these.

Command
node --version
python3 --version
git --version
Expected output (versions may differ)v18.19.0 Python 3.11.6 git version 2.43.0
Why this matters

Node 14+ is what runs orchestrator/Orchestrator.js — the small engine that tracks which agents have finished and writes .orchestrator-state.json so a run can resume (Step 15). Python 3.8+ is what several of the 150+ Kali tools the agents drive are written in or depend on (sqlmap, many OSINT scripts). Git is needed both to clone the repo and, later, for the git-forensics-style agent that inspects repository history. Skipping this check doesn't fail loudly — an old Node version tends to surface later as a confusing YAML/JSON parsing error deep into a run that can last most of a day, which is why it's worth 10 seconds now.

If a command says "not found"Install the missing tool: nodejs.org (Node 14+), python.org (Python 3.8+), git-scm.com (Git). On Windows, run these in Git Bash. Make sure Claude Code itself is also installed and signed in — that's the piece that actually dispatches the 106 agents.

3

Install the Kali toolbox (150+ tools)

What this does: installs the 150+ tools (nmap, sqlmap, ffuf, nuclei, hashcat, metasploit, frida, ghidra, and more) that agents call over SSH when they actually run tests. Run these on the Kali machine or VM — takes ~20–30 minutes.

Commands (run on Kali)
bash kali-setup/kali-init.sh        # one-time base setup: packages, directories, permissions
bash kali-setup/install-tools.sh    # installs 150+ tools (~20-30 min)
bash kali-setup/verify-tools.sh     # confirms tools are installed
Expected output (end of verify)✅ nmap - installed ✅ sqlmap - installed ✅ nuclei - installed 📊 Results: 7 found, 0 missing ✅ All required tools are installed!
Why this matters

The framework doesn't reimplement nmap, sqlmap, or hashcat — each agent is effectively a detailed prompt that knows how to drive a real tool and interpret its output. If a tool is missing, the agent that depends on it either fails outright or has to report a degraded, evidence-light finding that will likely get rejected at the Evidence gate (Step 11). Installing everything up front means no agent hits a missing-tool surprise 40 agents into a run.

Don't have a Kali box yet?Any Kali Linux 2024.x+ VM with 4GB+ RAM works — see kali-setup/README.md for VM setup notes.
4

Connect to Kali over SSH & run the health check

What this does: lets your control machine (where Claude Code runs) send tool commands to Kali securely, then confirms the connection and the key tools actually respond.

On the Kali machine — turn on SSH
sudo systemctl enable --now ssh
ip addr | grep inet          # find Kali's IP, e.g. 192.168.56.101
On your control machine — create a key, copy it, point the framework at Kali
ssh-keygen -t ed25519 -f ~/.ssh/kali_key -N ""
ssh-copy-id -i ~/.ssh/kali_key.pub kali@<kali-ip>
export KALI_HOST=<kali-ip> KALI_USER=kali KALI_KEY=~/.ssh/kali_key
bash orchestrator/kali-health-check.sh
Expected output🔍 Kali health check SSH connectivity... ✅ nmap... ✅ sqlmap... ✅ nuclei... ✅ ✅ Kali is ready.
Why this matters

SSH keys instead of a password mean the connection can be scripted without an interactive password prompt breaking automation partway through a 106-agent run — and it's auditable (each key can be traced to whoever generated it). The health check is a deliberately separate step from Step 10's full run: it fails fast on a bad IP, a closed SSH port, or a missing tool in under a minute, instead of you discovering the same problem 20 minutes into what's meant to be an approximately 15-hour test. Under the hood, every agent that needs a real tool calls orchestrator/kali-wrapper.sh, which is just a thin wrapper that SSHes to Kali, runs one command, and returns stdout/stderr back to the agent.

Windows noteUse $env:KALI_HOST="<ip>" in PowerShell instead of export. If the health check fails, recheck the IP/username/key before moving on — every agent depends on this connection.

Create an engagement (a folder per target)

What this does: every agent reads its input from one engagement folder. This scaffolds it with a config, a scope template, a credentials template, and empty evidence/report folders.

Command · sample name "acme-corp"
bash scripts/setup-engagement.sh acme-corp
Createsengagements/acme-corp/config.yaml engagements/acme-corp/scope.md engagements/acme-corp/.secrets.template engagements/acme-corp/evidence/findings/ engagements/acme-corp/report/
Why this matters

One folder per target is an isolation boundary, not just tidiness: it keeps one client's credentials, evidence, and report completely separate from another's, so you can have several engagements set up at once without any risk of cross-contamination (an agent testing acme-corp never sees another-client's .secrets). The whole engagements/ directory is git-ignored for the same reason — a client's target URL, test credentials, and findings should never end up in your commit history.

Pick any nameSomething short with no spaces, e.g. acme-corp, my-app, client01. Use the exact same name in every command from here on.

Why this matters

Use a dedicated test account, not a real user's or an admin's production login. Several agents (auth-flow, session-management, IDOR, rate-limit) deliberately try to break authentication and authorization logic — log in repeatedly, tamper with tokens, probe access boundaries. Pointed at a shared or production account, that same behavior can trigger account lockouts, fraud-detection flags, or password resets that affect a real person. Scoping the blast radius to a disposable test account is what makes aggressive testing safe.

.secrets is git-ignoredCredentials never get committed. Every agent that needs auth reads them from here at runtime, and the reporting agent automatically masks them (and any PII) before the HTML report is written.

Define scope & authorization — the safety gate

What this does: agents will not run against a target unless scope.md explicitly says testing is authorized. This is enforced before the first agent dispatches.

Command
nano engagements/acme-corp/scope.md
Required — exact line the engine looks for
authorization.confirmed: true
Sample scope.md content
# Engagement Scope

authorization.confirmed: true

## Target
- URL: https://staging.acme-corp.com

## In Scope
- Web application and its APIs

## Out of Scope
- Production database, third-party payment services

## Restrictions
- No DoS attacks; testing during business hours only
Why this matters

In most jurisdictions, actively probing a system for vulnerabilities without the owner's explicit consent is unauthorized access, regardless of intent — the same techniques that make a good pentest can constitute a crime without permission. scope.md is the technical control that forces that consent to exist, in writing, before any agent touches the target: it's not just documentation, the orchestrator refuses to dispatch Agent-001 (or any agent) if this line is missing. "In Scope" / "Out of Scope" also matters practically — it's what stops an agent from, say, wandering from a web app into a shared production database that wasn't meant to be tested.

Also fill inAUTHORIZATION_NAME / AUTHORIZATION_EMAIL from Step 6 should match the person named here — the reporting agent (Step 14) prints both as proof of sign-off.

Full agent catalog (real filenames): see the Agent Explorer below, or browse orchestrator/agents/ directly. Every agent maps to a Claude Code subagent type:

What a spec file actually containsOpen any file, e.g. orchestrator/agents/Agent-001-Reconnaissance.md — it reads like a briefing: Overview, Tools Integrated, Testing Approach (step by step), Validation Requirements, CVSS scoring guidance. When an agent is dispatched, this file's content becomes the prompt passed to the Agent tool.
Why this matters

Each of the 106 agents runs in its own isolated Agent-tool context — it doesn't see the other 105 agents' reasoning or conversation, only whatever slice of execution_context is explicitly handed to it (e.g. the surface map, or a prior phase's findings). That isolation is deliberate: it keeps every agent narrowly focused on one job instead of one giant, unfocused 106-topic conversation, and it's what makes running just one agent (Step 12) meaningful — you get the same quality of output whether it runs alone or as part of the full 106.

10

Initiate testing — run all 106 agents

What this does: tells Claude Code to dispatch all 106 agents in sequence, letting output from earlier agents feed later ones. This is the command that starts everything.

In Claude Code, type
Run full penetration test for acme-corp

What happens under the hood, per agent:

  1. Claude Code reads engagements/acme-corp/config.yaml, scope.md, .secrets (your URL + creds from Step 6), and the current execution_context (everything found so far).
  2. It loads the next agent's spec, e.g. orchestrator/agents/Agent-002A-SQL-Injection.md.
  3. It calls the Agent tool with subagent_type: "penetration-tester" (or security-auditor), passing that spec plus the relevant slice of execution_context (e.g. the surface map from recon) as the prompt.
  4. The subagent runs the real tools against Kali over SSH (via orchestrator/kali-wrapper.sh) and returns findings.
  5. Findings are written as JSON to engagements/acme-corp/evidence/findings/, following templates/finding-schema.json.
  6. Each finding passes the 4-layer validation gate (see Step 11) before it's added to execution_context for the next agent.
Expected output (start)🚀 Starting penetration test for: acme-corp ✅ Scope gate passed ✅ Evidence directories ready ▶️ Recon — Agent-001A / Agent-001B ✅ Agent-001A (Passive Recon) — 4 findings ✅ Agent-001B (Active Discovery) — 12 open ports ▶️ Web / API / Auth surface — Agent-002x / Agent-003x / Agent-004x ✅ Agent-002A (SQL Injection) — 2 findings ...
Why this matters

Agents run in sequence, not all at once, because later agents genuinely depend on earlier discoveries — there's no point testing SQL injection on an endpoint recon hasn't found yet, and exploitation agents need confirmed findings from surface-testing agents before they attempt anything deeper. execution_context is the mechanism that carries that forward: it's one growing JSON object threaded through every agent call, where each phase's validated output becomes the next phase's input — recon's surface map feeds web/API testing, which feeds exploitation, and so on through to the report. A full run typically takes approximately 15 hours precisely because of this chain: it can't meaningfully be sped up by running everything in parallel, and several individual agents (password cracking, WiFi handshake capture, full vulnerability scans) genuinely take real wall-clock time on their own.

Terminal alternativeYou can also drive it from a shell instead of asking Claude Code directly: bash scripts/run-pentest.sh acme-corp (validates config, then runs node orchestrator/Orchestrator.js acme-corp). The Node script itself doesn't call any AI — it tracks agent completion state so a run can resume; the actual agent dispatch still happens through Claude Code.

Understand the 4-layer validation gate

What this does: every single finding, from every agent, must pass all four gates below before it's added to execution_context or written into the final report. This is how the framework targets 0% false positives.

1

Format Validation

  • Valid JSON against finding-schema.json
  • All required fields present
  • Correct data types
→
2

Evidence Validation

  • Real HTTP request/response
  • Authentic tool output
  • Reproducible steps
→
3

Technical Accuracy

  • CVSS score justified
  • Impact is specific, not vague
  • No fabrication
→
4

Remediation Validation

  • Vulnerable + fixed code examples
  • Clear fix steps
  • Realistic effort estimate

A finding that fails any gate is rejected, not silently dropped — it's logged so you can see why. Only findings that clear all four gates reach validated_findings_only, which is the only thing the final report (Step 14) is built from.

This runs automaticallyYou don't invoke validation separately — it happens after every agent, as part of Step 10. This step exists so you understand why a finding might not show up in the report even though an agent flagged something.
Why this matters

Concretely: say an agent reports "possible reflected XSS on the search field" but can't produce an actual payload and the server's response that proves it fired — that finding fails Gate 2 (Evidence) and never reaches the report, even though the agent suspected something. This is the mechanism behind the framework's "0% false positive" goal — it's not that agents never guess wrong, it's that a guess without hard evidence, a justified CVSS score, and a working fix is stopped before it reaches a client-facing document. It also means a thin report isn't necessarily a clean target — check evidence/findings/ for rejected findings if you want to see what was suspected but not proven.

Run a single agent or targeted phase (alternative to the full run)

What this does: instead of all 106 agents, dispatch just the ones you need — useful for re-testing one area, a quick spot-check, or picking up where a partial run left off.

Example prompts you can type in Claude Code
Run the recon agent (Agent-001) for acme-corp and show me the surface map

Run Agent-002A-SQL-Injection.md against acme-corp's discovered endpoints

Re-run only the API security agents (Agent-003x) for acme-corp using
the existing surface map from evidence/findings/

Claude Code still: loads that agent's spec file, calls the Agent tool with the right subagent type, saves findings under the same evidence/findings/ folder, and runs them through the same 4-layer validation gate — it just skips the agents you didn't ask for.

Why this matters

The full 106-agent run and a single targeted agent use exactly the same pipeline (spec → Agent tool → findings → validation gate) — targeted runs aren't a lighter-weight shortcut, they just narrow the scope. The most common real use: a developer fixes the SQL injection Agent-002A found, and you want to confirm the fix without re-running all 106 agents and re-hitting the target for another 15 hours. It's also useful for a fast pre-check on one area (e.g. just auth) before committing to a full engagement.

Requiring an explicit yes/no here means nothing high-impact happens against a live system without a person consciously agreeing to it.

Why this matters

The three mapping standards exist so this report speaks the same language as tooling your organization probably already uses: OWASP Top 10 is the industry-standard list of the most critical web application risks (e.g. "A03:2021 – Injection"); CWE (Common Weakness Enumeration) is a much more granular catalog — think of it as a dictionary of specific bug categories (e.g. CWE-89 for SQL Injection); MITRE ATT&CK catalogs real-world attacker tactics and techniques, useful for threat-modeling conversations. A finding tagged this way can be dropped straight into a SIEM, a compliance audit, or a ticket without someone manually re-classifying it.

Machine-readable copyA report.json is written alongside report.html if you need to feed findings into another system (Jira, a dashboard, etc.).

Resume an interrupted run, re-run, or start a new engagement

What this does: wraps up the workflow — how to pick a run back up if it stops partway, and how to start fresh against another target.

Resume after an interruption — just run it again
bash scripts/run-pentest.sh acme-corp
# or, in Claude Code:
Run full penetration test for acme-corp

The orchestrator writes engagements/acme-corp/.orchestrator-state.json after every agent completes. On a re-run, already-completed agents are skipped and only the remaining ones dispatch.

Start testing a new target
bash scripts/setup-engagement.sh another-client
# then repeat from Step 6 (target URL & credentials) with the new name
Why this matters

State is written to a file rather than kept only in memory specifically so a resume is safe even if Claude Code was closed, your machine restarted, or the connection dropped — without that, an interruption at agent 60 of 106 would mean starting the entire ~15-hour run over, and hitting the target with duplicate traffic for everything already tested. Because each engagement is its own isolated folder (Step 5), starting a new target is just as safe: nothing from acme-corp leaks into another-client.
